## ۱. چرا اثبات صوری؟

اثبات‌های کاغذی هم‌چنان خطا دارند. یک «واضح است که» در میانهٔ استدلال می‌تواند یک حالت مرزی را پنهان کند. در نرم‌افزار هم همین را می‌شناسیم: برنامه‌ای که «به نظر درست می‌آید» تا تست یا کامپایلر چیزی نگفته است. اثبات صوری همان نقش کامپایلر را برای استدلال بازی می‌کند.

## ۲. گزاره‌ها نوع‌اند، اثبات‌ها مقدار

برای برنامه‌نویس، `n : Nat` یعنی «`n` مقداری از نوع `Nat` است». Lean همین را به منطق می‌برد (تناظر Curry–Howard [۴]):

| منطق | برنامه‌نویسی | در Lean |
|---|---|---|
| گزاره $P$ | نوع | `P : Prop` |
| اثبات $P$ | مقداری از آن نوع | `hp : P` |
| $P \to Q$ | تابع از $P$ به $Q$ | `P → Q` |
| $P \wedge Q$ | زوج | `P ∧ Q`، ساخته با `⟨hp, hq⟩` |
| $P \vee Q$ | اتحاد برچسب‌دار | `P ∨ Q` |

نخستین اثبات‌ها:

<LeanBlock code={`theorem two_add_two : 2 + 2 = 4 := rfl

theorem imp_const (P Q : Prop) : P → Q → P :=
  fun hp _ => hp

example (P Q : Prop) (hp : P) (hq : Q) : P ∧ Q := ⟨hp, hq⟩`} />

- `rfl` می‌گوید دو طرف با محاسبه یکی می‌شوند. `2 + 2` به `4` کاهش می‌یابد.
- `imp_const` یک تابع است: دو ورودی می‌گیرد و اولی را برمی‌گرداند. همین اثبات «از P نتیجه می‌شود که Q ⇒ P» است.
- `example` قضیهٔ بی‌نام است؛ مناسب آزمایش.

<Callout type="note" title="اثبات‌ها فقط درباره‌ی Prop اند">

یک گزاره از نوع `Prop` است و مهم نیست **کدام** اثبات داده شده؛ فقط وجودش مهم است. بر خلاف `Nat` که `3` و `4` دو مقدار متفاوت‌اند، همهٔ اثبات‌های یک گزاره برابر شمرده می‌شوند (proof irrelevance).

</Callout>

## ۳. تاکتیک‌ها و حالت هدف

نوشتن مستقیم لامبدا برای اثبات‌های بزرگ طاقت‌فرساست. با `by` وارد حالت **تاکتیک** می‌شویم: هر دستور، هدف فعلی را به هدف‌های ساده‌تر می‌شکند. Lean در هر لحظه **goal state** را نشان می‌دهد: فرض‌ها بالای `⊢` و حکمی که باید ثابت شود زیر آن.

<LeanBlock code={`theorem and_swap (P Q : Prop) : P ∧ Q → Q ∧ P := by
  intro h1
  obtain ⟨h2, h3⟩ := h1
  constructor
  · exact h3
  · exact h2`} />

حالت‌ها پس از هر خط:

```text
-- شروع
P Q : Prop
⊢ P ∧ Q → Q ∧ P

-- پس از intro h1
h1 : P ∧ Q
⊢ Q ∧ P

-- پس از obtain ⟨h2, h3⟩ := h1
h2 : P
h3 : Q
⊢ Q ∧ P

-- پس از constructor: دو هدف
case left   ⊢ Q
case right  ⊢ P
```

هر `·` یک هدف را می‌بندد. تاکتیک‌های اصلی و اثرشان:

| تاکتیک | اثر |
|---|---|
| `intro h` | از هدف `A → B`، فرض `h : A` را به متن اضافه می‌کند و هدف را `B` می‌کند |
| `exact h` | هدف را با فرض (یا عبارت) `h` می‌بندد |
| `constructor` | هدف `A ∧ B` را به دو هدف `A` و `B` می‌شکند |
| `left` / `right` | برای هدف `A ∨ B` یک طرف را انتخاب می‌کند |
| `obtain ⟨h1, h2⟩ := h` | فرض `A ∧ B` را باز می‌کند |
| `rcases h with h1 \| h2` | روی `A ∨ B` حالت‌بندی می‌کند و دو هدف می‌سازد |
| `apply h` | با `h : A → B` هدف `B` را به `A` تبدیل می‌کند (استدلال به عقب) |

### آزمایش

قضیه را انتخاب کن و با دکمه‌ها اثبات را بساز. تاکتیک نامناسب خطا می‌دهد. دکمهٔ «نمایش اثبات کامل» هم یک اثبات درست را با انیمیشن بازپخش می‌کند. نام فرض‌ها (`h1`، `h2`، …) به ترتیب ساخته می‌شود.

<figure>
  <TacticDemo client:visible />
  <figcaption>شکل ۳ (تعاملی) — شبیه‌ساز تاکتیک برای منطق گزاره‌ها. آنچه در کادر می‌بینی همان شکل goal state و متن اسکریپت Lean است.</figcaption>
</figure>

<LeanBlock code={`theorem or_swap (P Q : Prop) : P ∨ Q → Q ∨ P := by
  intro h1
  rcases h1 with h2 | h3
  · right
    exact h2
  · left
    exact h3

theorem imp_trans (P Q R : Prop) : (P → Q) → (Q → R) → (P → R) := by
  intro h1
  intro h2
  intro h3
  apply h2
  apply h1
  exact h3`} />

در `imp_trans` از هدف `R` شروع می‌کنیم. `apply h2` می‌گوید «کافی است Q را ثابت کنم»، `apply h1` می‌گوید «کافی است P را ثابت کنم» و `exact h3` همین را دارد.

### وقتی اثبات غلط است

اگر ادعا را با اثبات اشتباه بنویسی، Lean دقیقاً می‌گوید چه چیزی نمی‌خواند:

```lean
theorem bad (P Q : Prop) : P ∧ Q → Q := by
  intro h
  exact h
```

```text
error: Type mismatch
  h
has type
  P ∧ Q
but is expected to have type
  Q
```

در این مثال باید `exact h.2` نوشت (مؤلفهٔ دوم زوج). و اگر هنوز اثبات نکرده‌ای، `sorry` راه فرار است:

<LeanBlock code={`theorem unfinished (P : Prop) : P → P := by
  sorry`} />

Lean می‌پذیرد ولی هشدار `declaration uses sorry` می‌دهد. `sorry` یعنی «بعداً»؛ قضیه‌ای که `sorry` دارد ثابت نشده است.

## ۴. استقرا: اثبات برای همهٔ اعداد

اعداد طبیعی در Lean با دو سازنده تعریف می‌شوند: `zero` و `succ n` (یعنی $n+1$). هر عدد یا صفر است یا جانشین عددی کوچک‌تر. همین ساختار، اصل استقرا را می‌دهد: برای اثبات $P(n)$ برای همهٔ $n$، دو چیز کافی است:

1. **پایه:** $P(0)$.
2. **گام:** از $P(k)$ (فرض استقرا، `ih`) نتیجه شود $P(k+1)$.

<figure>
  <DominoDemo client:visible />
  <figcaption>شکل ۴ (تعاملی) — استقرا مثل دومینو: پایه اولین را می‌اندازد و گام استقرا هر دومینو را به بعدی وصل می‌کند. با ▶ جلو برو.</figcaption>
</figure>

<LeanBlock code={`theorem zero_add' (n : Nat) : 0 + n = n := by
  induction n with
  | zero => rfl
  | succ k ih => rw [Nat.add_succ, ih]`} />

چرا این کار اثبات لازم دارد؟ چون جمع روی آرگومان **دوم** تعریف شده است: `n + 0` با محاسبه برابر `n` است ولی `0 + n` نه. پس `0 + n = n` برای متغیر `n` مستقیماً `rfl` نیست و به استقرا نیاز دارد.

- `case zero`: هدف `0 + 0 = 0` است و با محاسبه درست است، پس `rfl`.
- `case succ`: هدف `0 + (k + 1) = k + 1`. قاعدهٔ `Nat.add_succ` آن را به `(0 + k) + 1 = k + 1` بازنویسی می‌کند و `ih : 0 + k = k` کار را تمام می‌کند. `rw` بعد از بازنویسی خودش `rfl` را امتحان می‌کند.

### مثال بزرگ‌تر: جمع ۱ تا n

ابتدا جمع را به‌صورت برنامه تعریف می‌کنیم و محاسبه‌اش می‌کنیم. بعد قضیه‌ای می‌نویسیم که برای **همهٔ** `n` برقرار است. ضرب در ۲ لازم است تا تقسیم نداشته باشیم:

<LeanBlock code={`def sumTo : Nat → Nat
  | 0 => 0
  | n + 1 => sumTo n + (n + 1)

#eval sumTo 10

theorem sumTo_formula (n : Nat) : 2 * sumTo n = n * (n + 1) := by
  induction n with
  | zero => rfl
  | succ k ih =>
    simp only [sumTo, Nat.mul_add, ih]
    simp only [Nat.add_mul, Nat.mul_one, Nat.one_mul]
    omega

#print axioms sumTo_formula`} />

خروجی واقعی:

```text
55
'sumTo_formula' depends on axioms: [propext, Quot.sound]
```

`#eval` یک نمونه را حساب می‌کند: $1+\dots+10=55=10\cdot 11/2$. قضیه ولی برای هر $n$ برقرار است و تست هیچ‌گاه این را نمی‌دهد. `omega` تصمیم‌گیر عددی Lean برای معادلات خطی روی اعداد صحیح/طبیعی است و جبر آخر را می‌بندد.

## ۵. Mathlib و پروژه‌های بزرگ

نوشتن همه‌چیز از صفر عملی نیست. **Mathlib** کتابخانهٔ ریاضی Lean است: جبر، آنالیز، توپولوژی و هزاران قضیه، با تاکتیک‌های قدرتمند مثل `simp`، `ring`، `linarith`. معمولاً کار روزمره این است که قضیهٔ مناسب را در Mathlib پیدا و ترکیب کنی. نمونه‌هایی که با Lean صورت‌بندی و تأیید شده‌اند (منابع باید پیش از استناد دقیق بررسی شوند):

- حکم‌های بسیار بزرگ مثل آنچه در پروژهٔ Liquid Tensor Experiment چک شد.
- بخش‌هایی از اثبات‌های جدید ترکیبیاتی و تحلیلی.

در مهندسی نرم‌افزار هم مشابه این‌ها را می‌بینی: Lean خودش برنامهٔ Lean است [۱]، و می‌توان خاصیت برنامه را کنار خود برنامه ثابت کرد؛ مثل `sumTo_formula` بالا.

<Callout type="warn" title="درست اثبات‌شده، اما ممکن است قضیهٔ اشتباهی باشد">

اگر تعریف `sumTo` را اشتباه می‌نوشتی و قضیه‌ای مطابق همان تعریف اشتباه ثابت می‌کردی، Lean می‌پذیرفت. قضیه‌ای مثل «برنامه‌ام درست است» فقط وقتی ارزش دارد که مشخصهٔ «درست» را درست نوشته باشی. همیشه `#print axioms` و تعریف‌ها را بخوان؛ اگر `sorryAx` یا آکسیوم ناخواسته ببینی، اثبات کامل نیست.

</Callout>

هزینهٔ دیگر زمان است: صوری‌سازی یک صفحه استدلال می‌تواند ساعت‌ها طول بکشد. در ازایش، چیزی می‌گیری که کاغذ نمی‌دهد: اطمینان مکانیکی، قابلیت بازاستفاده و جستجوی دقیق در قضیه‌ها.
